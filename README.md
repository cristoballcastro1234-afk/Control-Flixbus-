# Control FlixBus 2.0 — rama de preparación
Aplicación Cloudflare Pages + D1. La versión de producción no está modificada.
## Sincronización y cuotas gratuitas
- Se conserva el intervalo de 12 segundos en cada pestaña visible. Cada GET sin cambios lee únicamente la cuenta y una fila de revisión, además de los costes de índices. El tablero completo se recupera si cambia la revisión, la fecha o tras un guardado propio. No hay caché persistente de datos de buses.
- Aplicar también `migrations/0006_sync_ligera.sql` después de 0005, tanto en prueba como en producción. La migración 0006 es repetible y no elimina registros. Los triggers incrementan la revisión dentro de la misma operación que modifica horarios o turnos.
- El primer GET de cada día ejecuta la limpieza de respaldo. El Cron independiente sigue siendo imprescindible si no hay usuarios conectados. 
- Medir las cuotas de toda la cuenta tras el despliegue; 6 pestañas durante 16 h 10 min a 12 s implican aproximadamente 29.100 GET/día antes de otros accesos.
## Cambios
- Configuración permanente de horarios por destino y grupo (lunes a sábado / domingo). Se migran los 86 horarios existentes a lunes–sábado; **domingo queda sin horarios hasta que el administrador los configure**. Los tipos directo/indirecto (entrada al terminal de Rancagua) y terminal Sur/San Borja son opcionales para Santiago, tanto en el horario como en el registro del día.
- Registro de bus, hora planificada, llegada, salida, cancelación con motivo opcional, observaciones, quitar/restaurar servicio del día, buses extra. Botones Ahora con hora de Chile ajustada con el servidor.
- Actividad únicamente del día vigente (quién, cuándo, cambios); últimas 250 entradas visibles. Los datos operativos no se guardan en almacenamiento local, informes históricos ni archivos de respaldo propios. La cola de cambios es únicamente en memoria y descarta la fecha anterior al cambiar el día.
- El servidor calcula el día de Chile, nunca lo toma del reloj del operador. Los endpoints operativos eliminan registros de fechas anteriores; un Worker programado separado permite limpiar incluso sin usuarios conectados. La ejecución del Cron puede retrasarse: validar el cumplimiento de la política de privacidad con Cloudflare (retención de plataforma, D1 Time Travel, respaldos, logs y archivos PDF exportados quedan fuera del alcance de este código).
- Cambiar contraseña NO revoca la sesión. Eliminar/desactivar sí; reactivar obliga a iniciar sesión nuevamente. Los tokens de la versión anterior se renuevan una sola vez al desplegar.
## Pruebas y despliegue (NO ejecutar contra producción durante las pruebas)
1. Crear una base D1 de prueba y configurar su binding DB en un proyecto de vista previa independiente. Las configuraciones incluidas de origen contienen el identificador de la base existente. **No apuntar vistas previas ni el Worker de prueba a producción**. Usar un SESSION_SECRET de prueba.
2. Instalar dependencias y ejecutar npm run typecheck y npm test (Node 22.13 o superior). Para una base NUEVA: npm run db:migrate:local (o aplicar las migraciones a la base de prueba explícita). Para una base EXISTENTE con 0001–0004 ya aplicadas manualmente, aplicar solamente 0005 (una única vez, verificando columnas antes); no volver a ejecutar 0002/0003. El script db:migrate:v2:existing es remoto y apunta a la base configurada; no usarlo durante pruebas. Si se administra con D1 migrations apply, registrar las migraciones anteriores ya ejecutadas antes de usarlo en producción.
3. Arrancar npm run dev. Crear primer administrador en entorno de prueba, usuario operador, configurar domingo y probar los escenarios de abajo con datos ficticios.
4. Revisar captura de pantalla y usabilidad móvil; solo después de aprobación, coordinar corte de producción fuera del turno, aplicar la migración 0005 una vez y desplegar Pages desde main tras fusionar. El Worker de limpieza se debe desplegar por separado (npm run deploy:limpieza, revisando el binding) y configurar/verificar sus eventos Cron. NO desplegar sin autorización ni prueba de privacidad. El cron está cada minuto, sin endpoint HTTP público.

## Control 2.1
Aplicar una vez `migrations/0007_horarios_operativos.sql` en D1 para configurar rutas y domingos. Conserva los registros del día y horarios dominicales que ya existan. La programación se copia desde lunes a sábado y tiene IDs propios para que se pueda editar por separado. El tablero toma ruta y terminal del horario permanente, no de los datos antiguos de operación. En extras sin configuración se muestra Directo / Terminal Sur para Santiago. En móvil una salida se mueve a Salidas anteriores solo cuando máquina, llegada y salida son válidas y todos sus cambios están guardados. Cancelados o retirados no se marcan completos automáticamente; los retirados se consultan con su filtro. En escritorio se muestran todos los servicios; el intervalo sigue siendo 12 s.
