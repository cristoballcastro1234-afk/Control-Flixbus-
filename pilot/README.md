# Control FlixBus v3 — piloto aislado
NO fusionar a main ni usar datos reales. El piloto falla cerrado sin PILOT_DB y SESSION_SECRET. Usar un proyecto Pages nuevo (control-flixbus-piloto), rama v3-multioficina-piloto, salida public. No copiar ninguna vinculación o secreto de producción.
## Cloudflare
1. Crear cinco bases D1 nuevas: flixbus-piloto-sf, flixbus-piloto-stgo, flixbus-piloto-curico, flixbus-piloto-rgua, flixbus-piloto-scrz. Inicializar SF con pilot/sanfernando-consola.sql y las otras con pilot/nueva-oficina-consola.sql (una vez, bases vacías). SF contiene solo horarios de respaldo del repositorio, no usuarios ni turnos. Otras oficinas empiezan vacías. Si SF ya fue inicializada con el esquema de cuatro oficinas, aplicar una vez pilot/agregar-santacruz.sql solo en la base piloto SF. Ejemplo: npx wrangler d1 execute flixbus-piloto-sf --remote --file=pilot/sanfernando.sql --config wrangler.toml (si Wrangler requiere identificador, configurar el binding de la nueva base en una copia local; nunca seleccionar DB de producción).
2. Vincular en proyecto Pages piloto las bases como PILOT_DB, PILOT_SANTIAGO, PILOT_CURICO, PILOT_RANCAGUA, PILOT_SANTACRUZ respectivamente. Añadir SESSION_SECRET nuevo y exclusivo y SETUP_TOKEN aleatorio de alta entropía, como secretos, solo para el piloto. La creación inicial del administrador requiere SETUP_TOKEN; no publicarlo. Tras crear el administrador, puede eliminarse SETUP_TOKEN. Restringir acceso al proyecto de prueba mientras se crea el primer admin (setup público mientras no hay usuarios). No usar contraseñas reales.
3. Publicar worker independiente: npm install; npm run deploy:realtime (SQLite, sin URL pública), vincular Durable Object REALTIME, clase OfficeHub, script flixbus-realtime-piloto en Pages. Redeploy del piloto. Sin binding se usa consulta cada 60s; con WebSocket conectado, reconciliación cada 120s, ping/pong, renovación de sesión cada 10min, reconexión progresiva. Notificación solo tras POST exitoso y nunca incluye datos operativos. API sigue validando cada lectura/escritura.
4. Antes de cualquier uso real, configurar Worker de limpieza piloto con las cinco bases nuevas; cron 03:00/04:00 UTC cubre medianoche Chile continental según horario. Los GET también limpian datos viejos. Verificar expiración en las cinco bases antes de producción.
5. Crear admin de prueba y operadores por oficina. Comprobar aislamiento cambiando URL y oficina, dos dispositivos simultáneos, guardados concurrentes, desconexiones, revocación, medianoche, cuotas, pruebas de carga. No introducir datos reales.
## Alcance
Admin global, operadores limitados a una oficina, horarios y actividad separados, destinos iniciales provisionales para las nuevas oficinas (validar con cada terminal). GPS deshabilitado en piloto; GPS real de main no cambia. Enlaces públicos registrados para San Fernando, Curicó, Rancagua, Santiago Terminal Sur y Santa Cruz; las cinco oficinas tienen acceso directo en su tablero. Santiago solo Terminal Sur. Pendiente autorización de reutilización, normalización, horarios completos y consumo GPS por terminal. No se presume acceso técnico ni autorización para nuevas estaciones. Sincronización notifica e invalida; cada cliente consulta su propia API autenticada; no es cero consultas. Medir cambios y lecturas D1 para 22 o más dispositivos. No fusionar a producción sin revisión, migración y prueba de reversión.

## Horarios GPS dinámicos — versión de prueba
- Código: `worker/gps-piloto.mjs`, configuración `wrangler.gps-piloto.toml`. Nuevo Worker separado `flixbus-gps-piloto`. La rama main y su Worker GPS permanecen intactos.
- D1 piloto de cada oficina; consulta completa del día local **cada cinco minutos** mediante cron `*/5 * * * *` (no `0 */5 * * *`, que sería cada cinco horas).
- Aún no hay conexión activa: requiere Secret `GPS_API_KEY` configurado con acceso permitido por el proveedor y variable `PILOT_GPS_ENABLED=true`. Verificar primero las cinco estaciones revisando los logs. `PILOT_AUTO_HORARIOS=true` autoriza reemplazar SOLO la programación diaria del piloto cuando los datos estén completos. Ambas banderas deben estar ausentes o en false durante despliegue inicial.
- No se inventan horarios, no se adivinan destinos desconocidos, se rechazan respuestas parciales y se hace pausa automática si el proveedor responde 401, 403 o 429. Si no hay lectura válida se mantiene el último horario del día, o el respaldo local si aún no existe uno.
- El horario *scheduled* oficial no se confunde con el ETA estimado: se presenta la estimación aparte. El identificador de carrera se conserva entre cambios de hora para no perder máquinas, horarios reales ni cancelaciones. Los servicios retirados se confirman en dos lecturas válidas; los registros de turnos no se borran.
- La página piloto lee `programacion_oficial` en la base de cada oficina. El nuevo Worker no usa el cache ni la clave del Worker oficial de San Fernando, y las consultas del proveedor no se efectúan desde navegadores de trabajadores.
- Aún hay que comprobar acceso API permitido, rutas/terminales, cobertura diaria completa por oficina, ausencia de duplicados, cron, cuotas del plan y sincronización entre dispositivos antes de habilitar escritura automática o fusionar a producción.

- Cloudflare Worker Builds: usar Build command `node --check worker/gps-piloto.mjs` (no escribir `None`, Cloudflare lo intenta ejecutar literalmente); Deploy command `npx wrangler deploy --config wrangler.gps-piloto.toml`.

### Verificación previa a escritura (piloto)
- Con una credencial autorizada, activar solo PILOT_GPS_ENABLED=true inicialmente. Mantener PILOT_AUTO_HORARIOS=false y PILOT_AUTO_OFICINAS ausente. Se verifica normalización, cobertura disponible y asignación de slots contra D1 sin guardar programación ni notificar clientes. Los logs incluyen conteos por destino y respaldo, no la clave.
- Contrastarlos con el horario oficial completo de cada estación (incluidos destinos intermedios, terminales y servicios simultáneos). Una base nueva vacía no demuestra cobertura completa. Revisar al menos dos consultas completas consecutivas y un cambio de jornada; los conteos son diagnóstico, no prueba de cobertura del proveedor.
- Activar escritura solo para oficinas realmente verificadas: PILOT_AUTO_HORARIOS=true y PILOT_AUTO_OFICINAS con sus identificadores separados por coma (sanfernando,santiago,curico,rancagua,santacruz cuando todas estén verificadas). Sin esa lista no se escribe. Los nombres se refieren solo al piloto. Si se detectan servicios con el mismo destino y hora se conserva el respaldo hasta revisar la identidad en el tablero.
- Para detener la escritura, poner PILOT_AUTO_HORARIOS=false. Para detener también consultas externas, PILOT_GPS_ENABLED=false. No copiar claves de producción sin autorización del proveedor ni habilitar planes de pago.
