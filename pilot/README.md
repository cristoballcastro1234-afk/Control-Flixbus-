# Control FlixBus v3 — piloto aislado
NO fusionar a main ni usar datos reales. El piloto falla cerrado sin PILOT_DB y SESSION_SECRET. Usar un proyecto Pages nuevo (control-flixbus-piloto), rama v3-multioficina-piloto, salida public. No copiar ninguna vinculación o secreto de producción.
## Cloudflare
1. Crear cuatro bases D1 nuevas: flixbus-piloto-sf, flixbus-piloto-stgo, flixbus-piloto-curico, flixbus-piloto-rgua. Inicializar SF con pilot/sanfernando.sql y las otras con pilot/nueva-oficina.sql (una vez, bases vacías). SF contiene solo horarios de respaldo del repositorio, no usuarios ni turnos. Otras oficinas empiezan vacías. Ejemplo: npx wrangler d1 execute flixbus-piloto-sf --remote --file=pilot/sanfernando.sql --config wrangler.toml (si Wrangler requiere identificador, configurar el binding de la nueva base en una copia local; nunca seleccionar DB de producción).
2. Vincular en proyecto Pages piloto las bases como PILOT_DB, PILOT_SANTIAGO, PILOT_CURICO, PILOT_RANCAGUA respectivamente. Añadir SESSION_SECRET nuevo y exclusivo. Restringir acceso al proyecto de prueba mientras se crea el primer admin (setup público mientras no hay usuarios). No usar contraseñas reales.
3. Publicar worker independiente: npm install; npm run deploy:realtime (SQLite, sin URL pública), vincular Durable Object REALTIME, clase OfficeHub, script flixbus-realtime-piloto en Pages. Redeploy del piloto. Sin binding se usa consulta cada 60s; con WebSocket conectado, reconciliación cada 120s, ping/pong, renovación de sesión cada 10min, reconexión progresiva. Notificación solo tras POST exitoso y nunca incluye datos operativos. API sigue validando cada lectura/escritura.
4. Antes de cualquier uso real, configurar Worker de limpieza piloto con las cuatro bases nuevas; cron 03:00/04:00 UTC cubre medianoche Chile continental según horario. Los GET también limpian datos viejos. Verificar expiración en las cuatro bases antes de producción.
5. Crear admin de prueba y operadores por oficina. Comprobar aislamiento cambiando URL y oficina, dos dispositivos simultáneos, guardados concurrentes, desconexiones, revocación, medianoche, cuotas, pruebas de carga. No introducir datos reales.
## Alcance
Admin global, operadores limitados a una oficina, horarios y actividad separados, destinos iniciales provisionales para las nuevas oficinas (validar con cada terminal). GPS deshabilitado en piloto; GPS real de main no cambia. Pendiente definir identificadores de estaciones oficiales, autorización de reutilización, normalización, horarios completos y consumo GPS por terminal. No se presume acceso técnico ni autorización para nuevas estaciones. Sincronización notifica e invalida; cada cliente consulta su propia API autenticada; no es cero consultas. Medir cambios y lecturas D1 para 22 o más dispositivos. No fusionar a producción sin revisión, migración y prueba de reversión.
